# 实验结果：SSD 上的 Parquet，CPU / GPU 的瓶颈在哪里？

日期：2026-09-08。本文的 GPU 性能结果均为 **SSD → 主存中转 → GPU**，
不是已经验证成功的 GPUDirect Storage。真正 GDS 在本次机器上失败，见下文。

## 结论

1. **增加 SSD 有效，但不能笼统说“CPU 加盘收益有限”。** 从一盘到两盘，
   无压缩和 Snappy 的 CPU/GPU 时间都大约减半；这些配置首先受存储链路限制。
2. **GPU 优势取决于工作负载，不能把处理算子的差距归给解压。** 双盘 Zstd
   完整扫描+并行 SUM：CPU **2.690 秒**，GPU **2.242 秒**，约 **1.20×**。
   去掉 SUM，仅完整读取/解码：CPU **2.345 秒**，GPU **2.174 秒**，仅约 **1.08×**。
   初始 CPU 顺序列 SUM 的 1.38× 差距被优化后明显缩小，不作为主要性能结论。
   三次短扫描不是统计显著性证明；Zstd 纯扫描两者的 min–max 区间存在重叠。
3. **没有完成真实 GDS 与 CPU 的性能比较，也没有四盘结果。**
   这次得到了可复现的 CPU/GPU 中转对照、解码诊断，以及直读失败证据。
   它支持继续研究高带宽存储，但不能据此声称 GDS 的收益已经验证。

## 环境与数据

- AWS `g6.8xlarge`，孟买，按需；AMD EPYC 7R13，16 物理核 / 32 vCPU，
  128 GiB 主存，一块 NVIDIA L4（23,034 MiB 可见显存）。
- 两块各 450 GB 的本地 NVMe，独立 ext4，显式 `data=ordered`，不是 EBS 数据盘。
- Ubuntu 24.04，Linux `6.17.0-1020-aws`，NVIDIA 开源驱动 `595.91.07`。
- PyArrow `23.0.1`；cuDF/libcudf `26.08.01`；KvikIO `26.08.00`。
  实际安装的全部依赖见 [环境锁定文件](results/environment/requirements.freeze.txt)。
- 134,217,728 行 × 16 个 int64 列，逻辑数据 **16 GiB = 17.180 GB**。
  所有处理路径完整物化并对所有列求和，16 个结果逐一与生成时的校验值核对。
  无字典编码、无统计信息，避免元数据 COUNT 和列裁剪影响结论。
- 同样的数据生成三种 Parquet。下表字节数是**每份完整数据集**，不是显存占用：

| Parquet 压缩 | 文件大小（GB，十进制） | 相对逻辑数据大小 |
|---|---:|---:|
| 无压缩 | 17.184 | 100.03% |
| Snappy | 9.934 | 57.82% |
| Zstd level 3 | 5.875 | 34.20% |

具体配置、生成脚本、计时边界见 [README](README.md)。这是一组控制变量的整数
工作负载，不代表字符串、嵌套列、字典编码数据或完整 SQL 查询。

## 冷盘端到端：三次重复的中位数

统一使用八文件批次，即每批 1 GiB 解码后数据。时间包含读取、解压/解码、
物化和全部 SUM，并等待结果返回 CPU；不含数据生成、CUDA 初始化和缓存清理。
**主表使用 CPU 32 线程读取 + 16 列并行 SUM**，不使用最初顺序列 SUM 的较弱基线。

| 压缩 | CPU 单盘（s） | CPU 双盘（s） | GPU 中转单盘（s） | GPU 中转双盘（s） | 双盘 GPU 相对 CPU |
|---|---:|---:|---:|---:|---:|
| 无压缩 | 16.043 | 7.554 | 16.032 | 7.529 | 1.00× |
| Snappy | 9.153 | 4.282 | 9.109 | 4.180 | 1.02× |
| Zstd | 5.497 | 2.690 | 5.324 | 2.242 | 1.20× |

从单盘到双盘，CPU 的加速比分别为 **2.12× / 2.14× / 2.04×**，
GPU 为 **2.13× / 2.18× / 2.38×**。超过 2× 的数值不应解读为必然超线性扩展；
短时云存储读取有波动，只有三个样本，尚未做长时稳态或置信区间研究。

双盘 Snappy 的文件读取速率约 2.32 / 2.38 GB/s，CPU/GPU 接近；Zstd 则分别为
2.18 / 2.62 GB/s。不能直接比较不同 codec 的“文件 GB/s”来判断整体处理能力，
因为输入大小不同。完整的文件吞吐、逻辑吞吐、CPU 用量和每组 min–max
都保留在 [CPU 并行 SUM 汇总](results/cpu-parallel-sum-summary.md)、
[GPU 与初始 CPU 汇总](results/matrix-summary.md) 及对应目录的原始 JSONL。

## 最贴近解压/带宽问题的对照：完整读取/解码，不做 SUM

依然调用 eager `read_table` / `read_parquet` 物化全部 16 列，并对 GPU 同步。
不是元数据 COUNT：所有输入列都读取和解码，所有行数均核对，冷盘设备读量
等于整份文件。完整数值正确性由同一数据/引擎的 SUM 配置验证。

| 压缩 | CPU 双盘冷 / 热（s） | GPU 中转双盘冷 / 热（s） | 冷盘 GPU 相对 CPU |
|---|---:|---:|---:|
| 无压缩 | 7.529 / 1.596 | 7.518 / 1.539 | 1.00× |
| Snappy | 4.292 / 2.006 | 4.143 / 1.313 | 1.04× |
| Zstd | 2.345 / 1.846 | 2.174 / 1.435 | 1.08× |

这是判断 Parquet 读取/解码本身时应优先查看的表。
数据表明：当前两盘下，无压缩与 Snappy 主要仍受 I/O 限制；Zstd 计算侧影响
更明显，但 CPU/GPU 冷盘差距较小，不能声称解压性能出现数量级差异。
热缓存和显存预驻留结果显示 GPU 有更高潜力，真实高带宽 SSD/GDS 是否能
兑现该潜力尚未验证。详见 [scan-only 汇总及范围](results/scan-only-summary.md)。

## 热缓存对照

仅预热压缩文件的 Linux 页缓存，不保留解码后的表。GPU 仍需经过主存中转和 H2D。

| 压缩 | CPU 冷盘 / 热缓存（s） | GPU 中转冷盘 / 热缓存（s） |
|---|---:|---:|
| 无压缩 | 7.554 / 1.859 | 7.529 / 1.716 |
| Snappy | 4.282 / 2.464 | 4.180 / 1.491 |
| Zstd | 2.690 / 2.095 | 2.242 / 1.599 |

这是支持瓶颈判断的证据，不是可直接相减的独立流水线阶段。
此表 CPU 使用并行 SUM。Zstd CPU 的热缓存时间已占冷盘时间的约 78%，
但单盘到双盘仍有显著收益。GPU 中转路径的热缓存时间更短，说明有更大的
潜在存储扩展空间；**四盘扩展和 GDS 收益仍需实际补测**。

## 纯 I/O 与计量检查

16 个线程、每次 8 MiB 的 `O_DIRECT` 完整文件读取，对三种文件的中位数吞吐
分别约为单盘 **1.02–1.03 GB/s**、双盘 **2.04–2.10 GB/s**。
这是指定读取模式的对照，不是 SSD 的严格带宽上界；应用的缓冲/异步读请求
模式不同，实测速率可以高于它。某些首次重复明显更快，例如双盘 Zstd 纯读
为 1.532–2.803 秒，因此保留全部重复并报告中位数，而非挑选最快值。

正式冷盘样本的块设备读取量约等于整份 Parquet 大小；正式热缓存样本为零。
这里验证的是 **Linux 页缓存冷、NVMe 设备实际接收了读请求**，并未控制 SSD
控制器内部缓存，也不等同于测量 NAND 读取量。

首个 CPU Snappy 热缓存组与最终 GDS 诊断的清缓存发生重叠，检查发现其中一个
样本有约 15.45% 的文件量实际读盘。整组三次被剔除并重新运行；原始记录仍在
[excluded](results/excluded/)，未用于任何正式汇总。

## 预驻留输入：把解码和 SUM 分开

每批输入预先加载为 CPU 的主存字节缓冲区，或者 GPU 的压缩 `rmm.DeviceBuffer`；
加载和 H2D 不计时，完整 Parquet 读取/解压/解码与 SUM 分开计时。
下表仍是扫描全部 16 GiB 逻辑数据、三次重复的中位数。

| 压缩 | CPU 读取+解码（s） | GPU VRAM 读取+解码（s） | CPU 顺序 SUM（s） | GPU SUM（s） |
|---|---:|---:|---:|---:|
| 无压缩 | 0.783 | 0.354 | 0.892 | 0.106 |
| Snappy | 1.531 | 0.609 | 0.894 | 0.108 |
| Zstd | 1.292 | 0.983 | 0.882 | 0.107 |

这组证据尤其重要：CPU 的顺序列 SUM 本身占用明显时间，初始端到端差距不能
简单归因于解压。预驻留输入的 Zstd 读取/解码差距仅约 1.31×，Snappy 约 2.51×。
这里依然包含 Parquet 元数据、页解码、分配和物化，不是仅测 codec 算法。
CPU 预驻留控制按文件并行读缓冲区，与主实验 Dataset 路径不完全相同；不能
将其阶段时间直接从主实验相减。原始结果在 [resident](results/resident/)。

## 为什么不能称为 GPU 直读结果？

按 NVIDIA 文档配置了开源驱动、完整 BAR1、关闭 NVMe multipath、启用 PCI P2PDMA、
独立 ext4、KvikIO compatibility OFF，且 cuFile `allow_compat_mode=false`。

虽然 [gdscheck](results/environment/gdscheck.txt) 显示 `NVMe: p2pdma` 和平台检查成功：

- 两块 SSD，普通用户和 root 四组严格读取都失败。
- Python/KvikIO 返回 `Operation not permitted`；cuFile 底层日志显示
  `cufile p2p chunk read failed`、`Operation not supported`。
- [内核记录](results/gds-probes/kernel-nvme.txt) 显示对应 NVMe 读命令返回错误。
- 排除 Python 包装层后，apt 安装的原生 `gdsio -x 0` 仍然失败，退出码 255：
  [原生工具输出](results/gds-probes/native-gdsio.stderr)。
- Python wheel 使用 cuFile 1.18.1.6，原生工具来自 GDS 1.17.1.22；两个独立入口
  都失败。所有探测命令、返回码、stdout/stderr 均在 [gds-probes](results/gds-probes/)。

因此，本机暴露的 NVMe/P2P 链路不能完成严格直读；这不是仅靠 root 权限或
更改一个环境变量能解决的问题。**不能据此泛化为所有 EC2 型号都不支持 GDS**，
但这台机器不适合继续验证真正直读的性能。

## 大批次敏感性与显存约束

将批次从八文件（1 GiB 解码后数据）增至 32 文件（4 GiB），初始 SUM 工作负载的
双盘结果如下，CPU 此处仍是顺序列 SUM：

| 压缩 | CPU 1 GiB / 4 GiB 批次（s） | GPU 1 GiB / 4 GiB 批次（s） |
|---|---:|---:|
| 无压缩 | 7.586 / 7.736 | 7.529 / 7.598 |
| Snappy | 4.167 / 4.290 | 4.180 / 4.135 |
| Zstd | 3.104 / 3.027 | 2.242 / 未完成（内存池分配失败） |

成功的配置没有出现明显大批次收益，见 [batch32 汇总](results/batch32-summary.md)。
Zstd 的 4 GiB 批次在 16 GiB 和 20 GiB 池上限下均失败，原始错误分别保留在
[failed](results/failed/) 和 [batch32-pool20](results/batch32-pool20/)。
后一次池已增长到 18.164 GiB，又请求约 6.164 GiB 的扩容，超过配置上限。
这包含分配器行为、压缩输入和解压工作区，不能用“解码输出只有 4 GiB”推断
显存一定足够，也不能仅凭池上限错误断言不存在更节省内存的实现。
本次全部正式对比使用成功且校验通过的 1 GiB 批次，不混入失败配置的部分计时。

## 对后续计划的修正

原想法应收窄为：提高 SSD 并行度能降低 I/O 受限配置的时间；接近各自读取/
解码/处理上限后才会收益递减。GPU 的预驻留吞吐更高，有潜在扩展空间，
但当前数据不支持“CPU 加盘收益已很有限”的笼统结论：优化 CPU SUM 后，
三种 codec 单盘到双盘都约 2×。尤其不能将顺序 CPU 归约造成的差距当成解压差距。

下一台机器先用严格 GDS probe 和运行时计数验收真实数据路径，再做 1/2/4 SSD
扩展实验；不要只根据“有 NVMe + NVIDIA GPU”或 gdscheck 成功就推断能直读。
扩展实验还应增加长时间连续扫描，验证稳定带宽，并覆盖字典编码和字符串数据。

本实验独立于 LingoDB 生产代码，没有将 RAPIDS 加入项目构建依赖。

## 验证、成本和清理

- 离线校验通过：56 组有效配置、168 条计时记录；384 个 Parquet 分片在两个布局
  中逐一 SHA-256 一致。校验脚本无需 GPU 或第三方 Python 包。
- 四盘低价 Spot 无容量；有容量区报价超过 5 美元/小时，因此未启动四盘机器。
  双盘 Spot 也无容量，最终只有一台双盘按需实例成功启动。
- 计算报价约 **2.42 美元/小时**，加根卷和公网 IPv4 后仍低于 5 美元/小时。
  报价参考[当日实例价格列表](https://www.doit.com/compute/compute/aws/ap-south-1/g6.xlarge)。
  包含环境准备的总费用估算 **3.6–4.0 美元**，不是最终 AWS 账单。
- 07:44:09 UTC 启动，09:11:36 UTC 请求终止；正常回收延迟后追加强制终止。
  最终确认实例为 `terminated`、实验 EBS 卷为零；孟买和弗吉尼亚两个区域的
  项目运行/待启动/停止/回收中实例审计均为零。
- 原始计时、配置、失败记录和文件校验清单已取回。云端大数据随临时 SSD 一起
  删除，可用固定种子和锁定依赖重新生成。原始工具日志正文未修改；归档时仅将
  日志文件名中的冒号替换为连字符，以便跨平台检出。

机器生命周期与脱敏审计见 [resources.json](results/resources.json)，
离线校验摘要见 [validation.json](results/validation.json)。
